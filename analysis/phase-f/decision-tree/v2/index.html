From one flow record to a closed case: the analysis behind every number

Version 2 of the decision tree. Every stage shows its formula, the record's own numbers substituted into that formula, and the stored result. Numbers come from workings.json, recomputed from the routed copy of data/demo.db and compared with what the product stored (31 of 31 checks pass).

Rules: commit dc58a09. Numbers: workings.json, built by flowtree_workings.py from a copy of data/demo.db routed by scripts/materialize_flow_queue.py. Ground truth is from data/processed/demo_ground_truth.json and is never visible to the product.

How to read the numbers

The same words are used in every card below. Read this table first.

The eleven stages

A flow passes these stages in order. Each card shows the input, the analysis steps, the formula, the output and where the result is stored.

S1Read one flow — What does the sensor deliver for one flow?

Input

One row of the flow dataset: addresses, ports, protocol, byte and packet counts, timings, TCP flags.

Analysis

  1. The row is stored in flow_data. Its 88 attributes are kept in one JSON field, flow_features.
  2. Two names are kept for the rule engine: the dataset name and the rule field name, for example Dst Port is destinationPort.
  3. The model reads the 82 numeric columns listed in models/feature-columns.json.
  4. Labels are joined after prediction, for evaluation only. No detector reads them.

Formula

stored attributes = 88
model input columns = 82 (models/feature-columns.json)
rule engine named fields = 16

Output

One flow record with a source record id, for example AL-01958.

Stored in

flow_data (source_record_id, flow_features, src_ip, dst_ip, dst_port, protocol, duration, packets, bytes)

Limits

  • The demo data is recorded traffic from 2018-02-14 to 2018-03-01, not live traffic.
  • Six stored attributes are not model inputs; they identify the flow rather than describe it.
S2Match signature rules — Does a written rule describe this flow?

Input

The 16 named flow fields.

Analysis

  1. Every rule in rules/ is tested. Each rule holds conditions over named fields.
  2. A condition is one of four tests: equality, a minimum, a maximum, or a list of allowed values (oneOf).
  3. A rule matches only when every one of its conditions is true. The matched conditions are stored with the observed value, so a human can check the claim without the rule file.
  4. sig is the largest severity score of the matched rules: Low 0.40, Medium 0.60, High 0.80, Critical 0.95. No match gives sig = 0.

Formula

rule matches  <=>  every condition true
sig = max(severity_scores[rule.severity]) over matched rules
no match -> sig = 0

Output

sig, and the list of matched rules with their conditions.

Stored in

alerts.signature_severity, alerts.signature_rules

Limits

  • A rule proves a pattern, not intent. The SOC reason to keep rules is a claim a human can check.
  • On this dataset the rules add no detection the model misses; they add checkable reasons.
S3Score the flow with the model — What does the trained model say, and how strongly?

Input

The 82 numeric features of the flow.

Analysis

  1. The model is an XGBoost classifier with 8 classes: Benign, Botnet, Brute Force, DDoS, DoS, Infiltration, Port Scan, Web Attack.
  2. It outputs one raw margin per class; a softmax turns the margins into probabilities that sum to 1.
  3. The highest probability gives the predicted class and its confidence.
  4. The malicious probability used for scoring is 1 minus the probability of Benign, not the confidence. A flow can be split between two attack classes and still be near certain to be an attack.
  5. TreeSHAP splits the margin for the predicted class into a base value plus one contribution per feature. The model checks that base plus contributions equals the margin, within 0.0001.

Formula

P(class) = softmax(raw margins)
confidence = P(predicted class)
ml = 1 - P(Benign)
raw margin = base value + sum(feature contributions)

Output

Predicted class, confidence, ml, and the strongest supporting and opposing features.

Stored in

alerts.ml_predicted_class, alerts.confidence, alerts.ml_probability, alerts.shap_attributions

Limits

  • Accuracy is measured against 2018 labels; it is not a promise about today's traffic.
  • Only the 5 strongest supporting and 5 strongest opposing contributions are stored, not all 82.
S4Fuse the two detectors — Which evidence class is this, and what is the score?

Input

sig, the matched rules' classes, the predicted class and ml.

Analysis

  1. If a rule matched and the model predicts a class that a matching rule asserts, the evidence is corroborated. Two independent detectors agree.
  2. If a rule matched and the model predicts another class, the evidence is signature_override: a checkable claim the model disputes. Always reviewed.
  3. If no rule matched and the model predicts an attack, the evidence is ml_only.
  4. If neither flagged the flow, the evidence is none.
  5. The score is then computed by one formula for the four cases.

Formula

corroborated:       min(100, max(sig, ml) x 100 + 5)
signature_override: sig x 100
ml_only, none:      ml x 100
score rounded to 2 places

Output

Evidence class, score, attack category, and whether review is required.

Stored in

alerts.evidence_class, alerts.detection_score, alerts.attack_category, alerts.requires_review

Limits

  • The +5 is a bonus for agreement, not extra certainty; it is clipped at 100.
  • signature_override is always review-flagged, and feedback cannot lower it (invariant I3).
S5Label the severity — How bad is this finding, given its class?

Input

The score and the attack class.

Analysis

  1. First the score selects a band: Informational below 1, Low from 1, Medium from 40, High from 70, Critical from 80.
  2. Then the attack class caps the band. The cap is read from config/severity-chart.json, which carries a CVSS v3.1 score per class.
  3. The final severity is the weaker of the band and the cap. Severity never exceeds the cap, and never exceeds the band.

Formula

band = Critical if score >= 80, High if >= 70, Medium if >= 40, Low if >= 1, else Informational
severity = min_rank(band, ceiling[attack_class])

Output

One severity label, and is_critical = score >= 80.

Stored in

alerts.severity, alerts.is_critical

Limits

  • Before the cap existed, 994 of 996 flagged alerts read Critical, across all seven attack classes.
  • The cap is the reason a DoS alert at score 100 is Medium, and so cannot become a Tier 2 candidate.

S6Group flagged flows — Which alerts are one event?

Input

Every flagged alert, with its source IP and time.

Analysis

  1. Alerts are sorted by time.
  2. The first alert from a source IP opens a group. The next alert from that IP joins the group when it is within 30 minutes of the previous member.
  3. Because the test is against the previous member, not the group start, a steady attack chains into one group that can span hours. Each step must still be within 30 minutes.
  4. The first member is the representative: its detection facts speak for the group in the queue.
  5. Unflagged flows are never grouped. Each one is its own queue item.

Formula

joins group  <=>  time(alert) - time(previous member from same source IP) <= 30 minutes

Output

One group per event: member count, first and last time, grouping key.

Stored in

alert_groups, alert_group_members

Limits

  • The group takes the representative's class. A mixed group therefore shows one class, although its members may differ.
  • Grouping is by source IP only; a distributed attack from many IPs becomes many groups.
S7Route the queue item — Who handles it: Tier 2 automatically, a Tier 1 decision, or routine Tier 1?

Input

The group's best member (score, evidence class), the class severity, and the routing policy.

Analysis

  1. E1, automatic: a member scores 80 or more and is corroborated, or a linked Suricata alert has severity 2 or lower. The whole group becomes a Tier 2 case with no Tier 1 action.
  2. The E1 rate limit allows 5 new automatic escalations per minute; the sixth becomes a candidate instead.
  3. E3, candidate: the best member scores 90 or more and its class severity is 7 or more, or the two detectors disagree on the class. The item goes to Tier 1 with a recommendation that a Tier 1 analyst must confirm or reject.
  4. Nothing matched: routine Tier 1.
  5. If routing throws an error, the item goes to routine Tier 1. Routing never closes or lowers an alert.

Formula

E1 = score >= 80 and (corroborated or linked Suricata severity <= 2)
E3 = score >= 90 and class severity >= 7, or the detectors disagree
else routine Tier 1

Output

handling_route (tier2_case or tier1_review), tier2_recommended, the reasons, and the priority.

Stored in

operational_triage_state_v2, operational_system_routing

Limits

  • E3 alone opened 342 wrong escalations on the stress set (precision 0.4722), which is why E3 needs a human.
  • Score alone does not make a candidate: DoS and Brute Force sit below severity 7.
S8Tier 1 work and verdict — Who takes it, what did they decide, and what does that change?

Input

The queue item.

Analysis

  1. Opening the row claims it: status in_review, owner recorded. A claim expires after 15 minutes idle; the owner or an admin with a reason can release it.
  2. A candidate shows the reasons and two buttons: Escalate to Tier 2 (+15, opens a case) or Keep in Tier 1 (closes the recommendation, records that an analyst decided).
  3. A verdict converts the outcome to the approved feedback category and asks for a score change: Confirmed Malicious +10, Suspicious 0, Expected Activity -15, False Positive -30, Escalate +15.
  4. The change passes the guardrails before it is applied. The requested and the applied change are both stored.
  5. The verdict also writes to family learning, which moves similar alerts only after 3 agreeing verdicts at agreement 0.67 or more.

Formula

requested delta: confirmed +10 . suspicious 0 . expected -15 . false positive -30 . escalate +15
applied = clamp and floor the change (see S9)

Output

Work status, verdict event, current score, feedback event.

Stored in

analyst_work, analyst_work_events, analyst_verdict_events, feedback_events

Limits

  • A verdict on a group is recorded on the representative; family learning carries it to unjudged members.
  • A verdict on an external Suricata alert writes no approved feedback: there is no approved-engine row for it.
S9Guardrails on the score change — How much of the requested change is applied?

Input

The requested change and the alert's score, class and protection state.

Analysis

  1. The change is capped at -30 and +20.
  2. A negative change cannot take a Critical alert (score 80 or more) below 70, or an Infiltration alert below 75. The floor applies only to an alert that started at or above it, so a floor never raises a score.
  3. The result is clamped to 0-100. Each intervention is stored with its configured value, the original value and the applied value.
  4. A signature_override alert cannot be lowered by feedback at all: the change is rejected.

Formula

applied = requested, capped to [-30, +20]
if protected and score_before >= floor: applied = max(applied, floor - score_before)
score_after = clamp(score_before + applied, 0, 100)

Output

The applied change, the action (applied, capped, rejected), and the list of interventions.

Stored in

feedback_events (original_score, requested_delta, actual_delta, guardrail_action), alerts.combined_score

Limits

  • The queue score is not stored. It is read as routing priority + (current score - detection score), clamped to 0-100, so the two cannot disagree.
S10Tier 2 case — How does a case move, and what closes it?

Input

A case created by policy (E1) or by an analyst (Escalate).

Analysis

  1. Start investigation records who started it and why, and moves the case from open to investigating.
  2. Record conclusion stores the finding, the final classification and the reason.
  3. Resolve records the resolution and the person. Resolve stays unavailable until a conclusion exists.
  4. A resolved case is read-only. A response recommendation can be approved; it is never executed by the product.

Formula

open -> investigating -> resolved
resolve requires a recorded conclusion

Output

Case status, revision, conclusion, resolution, and an event log.

Stored in

tier2_cases, tier2_case_state, tier2_case_events

Limits

  • A case does not re-score the alert. Its conclusion is recorded evidence, not feedback.
S11What the analyst sees — Where does each number appear on screen?

Input

The stored rows above.

Analysis

  1. The queue sorts by severity first, then unflagged items last, then queue score, then time.
  2. The row shows the representative's severity and score.
  3. The alert panel shows the evidence class, why Tier 2 was recommended, the rule conditions with observed values, and the model's strongest supporting features.
  4. History and notes name the person, never a number.

Formula

ORDER BY severity rank DESC, unflagged last, queue score DESC, time DESC, ref ASC

Output

The analyst's screen.

Stored in

read from the rows above; nothing new is stored

Limits

  • The number on a queue row is the operational priority stored at routing time. The sort key is the queue score, which adds the verdict change. After a verdict the two differ, and the row does not show the new value.

The thirteen decisions

Each decision is one branch point in the tree. The stage line links back to the stage card above.

N1What do the detectors say?decision

dataType alert · stage S4

Formula

corroborated if a rule matched and the model predicts a class a matching rule asserts; signature_override if a rule matched and the model disagrees; ml_only if only the model flags; none otherwise

Algorithm

  1. Compare the predicted class with the class of every matched rule.
  2. A match on any rule class is corroboration; the class itself is the predicted class.
  3. A rule with no model agreement is still evidence, but a disputed claim must be reviewed by a human.

Code

packages/detection/fusion/cef.py:226-238

Why a SOC needs this

The evidence class tells the analyst what kind of proof exists: a checkable rule, a model opinion, or both.

If the other branch is taken

On signature_override the alert is always review-flagged and feedback cannot lower it.

Watch out

The rule and the model can agree on the class but not on the story: a port-21 rule and a Brute Force prediction agree on Brute Force while the rule was written for FTP.

Evidence

tests/test_fusion.py, invariants I1-I4 (30 tests)

N2Score and severityprocess

dataType alert · stage S4–S5

Formula

score = min(100, max(sig, ml) x 100 + 5) when corroborated, sig x 100 when the rule overrides, ml x 100 otherwise; severity = band(score) capped by class

Algorithm

  1. Take the larger of the rule strength and the malicious probability, scale it to 0-100, and add 5 only when both detectors agree.
  2. Clip at 100.
  3. Label the band, then cap it by the class ceiling.

Code

packages/detection/fusion/cef.py:229-241, 119-138

Why a SOC needs this

Confidence says how sure the model is; the class says how much the finding is worth. One number cannot answer both.

If the other branch is taken

Without the class cap every attack reads Critical, which destroys the queue order.

Watch out

A score of 100 does not mean Critical severity. The cap decides.

Evidence

994 of 996 flagged alerts read Critical before the cap (packages/detection/fusion/cef.py:107)

N3Was the flow flagged?decision

dataType alert · stage S6

Formula

flagged  <=>  evidence_class != none

Algorithm

  1. Any flow the detectors flagged enters grouping.
  2. A flow with no evidence is kept as a single queue item instead, below every flagged item.

Code

scripts/materialize_flow_queue.py:30-32, 142-150

Why a SOC needs this

A missed attack must stay findable. Grouping by source IP would hide one attack among that host's benign flows.

If the other branch is taken

The flow still appears in the queue, so a human can find and confirm it. Record E is the proof.

Watch out

Unflagged does not mean harmless: record E is an attempted Web Attack the model called Benign.

Evidence

record E (AL-03086); 4,004 unflagged flows on the demo data

N4Group by source IPprocess

dataType group · stage S6

Formula

joins the open group  <=>  time - time(previous member, same source IP) <= 30 minutes

Algorithm

  1. Sort flagged alerts by time.
  2. Keep one open group per source IP.
  3. Join the open group when the gap to the previous member is 30 minutes or less; otherwise open a new group.
  4. Record the member count and the first and last time.

Code

scripts/materialize_flow_queue.py:61-75

Why a SOC needs this

One attack produces hundreds of near-identical alerts. The analyst works one item per event, not per flow.

If the other branch is taken

Without grouping the demo data would show 996 items instead of 81.

Watch out

The window chains. Record A's group spans 96.4 minutes while every step is 5.1 minutes or less.

Evidence

996 flagged alerts to 81 groups on the demo data

N5E1: auto-escalate?decision

dataType op · stage S7

Formula

score >= 80 and (corroborated or linked Suricata severity <= 2), limited to 5 new escalations per minute

Algorithm

  1. Test the group's best member.
  2. Require two agreeing detectors, or a Suricata alert of severity 2 or lower.
  3. Open a Tier 2 case with decision_source system_policy and no analyst action.

Code

packages/detection/flow_routing.py:90-134

Why a SOC needs this

A clear, corroborated, severe event should not wait for a click. Requiring two detectors stops one detector opening a case alone.

If the other branch is taken

The item falls to E3 or routine Tier 1, where a human decides.

Watch out

An E1 case cannot be claimed in Tier 1: it is already in Tier 2.

Evidence

N6Tier 2 candidate?decision

dataType op · stage S7

Formula

(score >= 90 and class severity >= 7) or the detectors disagree on the class

Algorithm

  1. Test the group's best member.
  2. Compare the class severity with 7.0, not the score.
  3. Recommend, never decide: the item stays in Tier 1 with a reason.

Code

packages/detection/flow_routing.py:135-171

Why a SOC needs this

The machine can see a pattern a human should look at, but the decision to spend Tier 2 time is a human judgement.

If the other branch is taken

Routine Tier 1, no recommendation, and the analyst still sees every field.

Watch out

DoS at 6.5 and Brute Force at 5.0 are below the line, so a score of 100 can still be routine. Record D is that case.

Evidence

N7Fail-safeprocess

dataType op · stage S7

Formula

on exception -> routine Tier 1, with the reason recorded

Algorithm

  1. Catch any routing error.
  2. Route to Tier 1 with a reason that names the failure.
  3. Never close, dismiss or lower an alert on error.

Code

packages/detection/flow_routing.py:161-165

Why a SOC needs this

A software fault must not hide an alert or open a case by mistake.

If the other branch is taken

Not exercised on the demo data: 0 of 4,085 routes took this path.

Watch out

A fail-safe that routes silently would hide the fault; the reason is stored and visible.

Evidence

dataType work · stage S8

Formula

open row -> status in_review, owner = analyst; idle 15 minutes -> claim expires

Algorithm

  1. Record the claim when the analyst opens the row.
  2. Expire an idle claim after 15 minutes.
  3. Allow the owner or an admin with a reason to release it.

Two analysts must not work the same alert, and a claim left by someone off shift must not block it.

N9Why Tier 2: escalate or keep?decision

dataType op · stage S8

Formula

Escalate -> Tier 2 case + feedback 'escalate' (+15); Keep in Tier 1 -> decision_source analyst, the recommendation closes

Algorithm

  1. Show the reasons that produced the recommendation.
  2. Require a reason for either choice.
  3. Escalate opens a case and records +15 through the guardrails; Keep closes the recommendation and keeps the stored flag as history.

Why a SOC needs this

The machine recommends; a human decides, states why, and that reason becomes part of the audit record.

An unanswered recommendation stays open, so the next analyst sees it.

Watch out

N10Verdictdecision

dataType verdict · stage S8

Formula

confirmed_malicious +10 . suspicious 0 . expected_activity -15 . false_positive -30

Algorithm

  1. Cap the requested change.
  2. Hold a protected alert at its floor, but only if it started at or above the floor.
  3. Clamp the result to 0-100.
  4. Store the requested value, the applied value and every intervention.

N12Family learning gateprocess

dataType verdict · stage S8

Formula

a family moves only after 3 agreeing verdicts at agreement >= 0.67

Algorithm

  1. Count the effective verdicts of the family.
  2. Require at least 3.
  3. Require the dominant verdict to hold 0.67 or more of them.
  4. Only then move the unjudged members.

One wrong verdict must not re-rank a whole family of similar alerts.

A group verdict counts once per family, not once per member.
