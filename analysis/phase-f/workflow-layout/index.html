Dual chain workflow: one capture, two detectors, one queue

The same packets feed two chains in parallel. The flow chain detects and groups; Suricata gives a second, named opinion. Both arrive in one queue, behind one login, and both learn from analyst verdicts through the same rule and the same guardrails. Sections 3 and 4 explain where the chains combine and how a family learns.

3. Where the two chains combine

The chains run apart from packet to routing. They meet at six points. The last one, the join (3.6), makes one queue item per connection. Each point below gives the mechanism, the table or file, and what it did on the full capture.

3.1 One packet, two readings

Every packet is read twice. CICFlowMeter turns each connection into one flow record. Suricata matches the same packets against the ET Open rules. The replay builder (scripts/build_packet_replay.py) links each Suricata alert to the flow record of the same connection (5-tuple and time). The queue joins the two on the connection's Community ID (section 3.6), so a connection that both chains read is one queue item, not two.

Only 6 alerts overlap: all are ET SCAN Potential SSH Scan from 13.58.98.64, inside the flow chain's brute-force group from the same host. 3.2 Each chain compresses its own alerts first

Flow chain — grouping (packages/detection/flow_queue.py). A flagged flow joins the open group of its source IP when it arrives within 30 minutes of that group's last member (config/flow-routing-v1.json, groupWindowMinutes); otherwise it opens a new group. Each group is one queue item: its first member is the representative. An unflagged flow is never grouped (decision D4): grouping would hide a missed attack among the same host's benign flows.

3.6 The join: one queue item per connection, the more severe reading shown

Match (packages/detection/cross_chain.py, run by the Packet Replay after each step's Suricata admission). Each admitted Suricata item gets the Community ID of its connection: version 1 of the open standard that Suricata, Zeek and most SIEMs use (1: + base64 of the SHA-1 of seed, the two addresses, the protocol number and the two ports, with the endpoints ordered so both directions give the same ID). The flow records with the same Community ID are the candidates. A 5-tuple can repeat within the capture (27,516 flows, fewer distinct 5-tuples), so the flow that started last at or before the Suricata alert is the connection. The implementation reproduces the specification's published test vector.

Winner. The two items are compared on three keys, in order:

  1. severity band on the one queue scale (queue_severity.py: critical, high, medium, low);
  2. route: tier2_case before tier1_review;
  3. operational priority.

The higher item is shown; on a full tie the flow item is kept. The scores are never averaged or added: the two chains measure different things (deck: "evidence-aware fusion, not a weighted sum"), and severity-first is the queue's existing rule (decision C9). A flow group is compared as a whole: its representative item.

Effect. The weaker item is hidden from the queue, the summary counts and the workspace count. It is not deleted: its row, scores, routing, audit and family learning stay, and the link is stored in the append-only table cross_chain_links (migration 27) with the Community ID, both items, the item shown, the item hidden and the reason.

4. Family learning: how one verdict teaches many alerts

A verdict does two things. It moves the judged alert at once, inside the guardrails. And it counts toward the alert's family: once 3 verdicts in one family agree (agreement ≥ 0.67), every member that nobody judged moves too. The judged alerts keep their own verdict. Both chains use the same effects, the same guardrails and the same quorum; only the family key differs.

The family change is also scaled by the family's severity weight (formula C1): a low-weight signature can move the full −30; a critical one moves much less. A severe threat is the hardest to talk down.

4.7 How to show it on demo day

  1. Let the replay reach step 24 or later (the flow family is complete at step 24; the Terminal Server family has its 3rd alert at step 9).
  2. As g.ang, search Terminal Server. Open two rows that are not the top one, and record False Positive on each (verdicts 1 and 2: nothing else moves yet).
  3. On stage, open a third row and record False Positive. The rows still marked Available drop from 40 to 10.
  4. Search 131.202.240.72 and repeat on the flow family: the other Available row drops from 36.49 to 6.49.
  5. Optional: one false positive on an ETERNALBLUE alert shows the floor: 85 → 70, never lower.
Limits to state. The flagged-flow family key has no host, so a quorum would reach every host on that port (the guardrails bound the size of the move, not its reach). A verdict changes the queue order; it never changes the detector, the routing route or the Tier 2 decision. The frozen V3.1 evaluation was run before Suricata reranking existed.

8. Run it

  1. Build the replay input once: python scripts/build_packet_replay.py.
  2. Open http://127.0.0.1:5173. Sign in as admin / admin-demo. Open Operational Workspace.
  3. To start from 0 alerts: click Reset Replay (it works while Replay is active and while analysts hold claims; analysts move to Operational).
  4. Choose Packet Replay. Click Prepare Replay, then Activate.
  5. Click Start Arrivals for one step every 5 seconds (160 steps ≈ 13 minutes), or Next Step / Next 5 Steps.
  6. Sign in as g.ang / analyst-demo in a second browser. New items arrive in the queue as the steps run.

9. What this page does not show

  • R2 is large. 10,383 unflagged flows each become one low-priority Tier 1 item (decision D4). This is product behaviour, not a replay artefact.
  • Stale reason text on R1. A group is routed once, when its first members arrive. The stored reason gives the group size at that time. The group then grows (to 5,100 and 11,613 flows).
  • Review is automatic in the replay. S3 is recorded in the preparing Admin's name with a fixed reason. In Operational, an analyst makes each S3 decision.
  • Recorded traffic, not live traffic. The model was trained on this testbed's dataset.
  • The join (section 3.6) hides the weaker reading of a connection. The alert panel does not yet show the hidden reading; it is stored in cross_chain_links. The data trace below still shows both readings.
  • The cross-chain escalation rule E1-suricata is not wired into the replay path (section 3.5).
  • Family predictions in 4.4 are computed with the product's functions, not run; the runs are in 4.6.
