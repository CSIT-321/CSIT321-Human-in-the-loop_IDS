Dual chain workflow: one capture, two detectors, one queue

The same packets feed two chains in parallel. The flow chain detects, groups and learns from analyst verdicts. Suricata gives a second, named opinion. Both arrive in one queue, behind one login.

1. Layout

One sign-in page, one API, one database per workspace. The Admin chooses the workspace: Operational or Replay. Every analyst then sees that workspace's single queue.

6. Run it

  1. Build the replay input once: python scripts/build_packet_replay.py.
  2. Sign in as admin. Open Workspaces.
  3. Choose Packet Replay. Click Prepare, then Activate.
  4. Click Start for one step every 5 seconds, or Next Step / Next 5 Steps.
  5. Sign in as g.ang in a second browser. New items arrive in the queue as the steps run.

7. What this page does not show

  • R2 is large. 10,776 unflagged flows each become one low-priority Tier 1 item (decision D4). This is product behaviour, not a replay artefact.
  • Stale reason text on R1. A group is routed once, when its first members arrive. The stored reason gives the group size at that time. The group then grows (to 5,100 and 11,613 flows).
  • Review is automatic in the replay. S3 is recorded in the preparing Admin's name with a fixed reason. In Operational, an analyst makes each S3 decision.
  • Recorded traffic, not live traffic. The model was trained on this testbed's dataset.
  • The other-chain link is by 5-tuple and time. It is shown here; the product does not yet show it in the alert panel.
