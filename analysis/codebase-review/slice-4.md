## Challenges to the team's assumptions
- Fact 1 is necessary but not sufficient. Materializing the 996 flow alerts puts them in the Active queue, but the claim and verdict gates additionally require an `operational_system_routing` row; only `system_routing.py:143` writes that table and `system_routing.py:84-86` restricts it to bundled Suricata evidence, so no projected flow alert can be claimed or receive a verdict (S4-01). `admit-tier1` is not a workaround: `routing.py:128-138` updates triage only.
- Fact 2 understates the gate. The supported historical non-bundle external path (`external_admission.py:173-186`) also admits alerts to `tier1_review/triage` without a system-routing row, and that path is used throughout the current tests (`tests/legacy_suricata_fixture.py`, `tests/test_selective_review.py`, `tests/test_triage_memory.py`). Those Tier 1 alerts are equally unworkable, so the problem is not specific to flow projection.
- The stated goal "the analyst can escalate, keep in Tier 1, or record a verdict" is only partly present in the console: `apps/web/src/pages/analyst/V2RoutingPage.tsx:55` filters routing actions to `manual_escalate`, so `admit_tier1`, `approve_tier2` and `reject_tier2` (the explicit keep-in-Tier-1 decision) are API-only.
- Fact 5's "investigation notes" cannot be restored by a UI change alone: the V2 API has no Tier 1 note command (`tier2_case_routes.py:90` is case-scoped; `analyst_verdict.py:13-18` has only outcome and reason), and the legacy `/api/alerts/{ref}/notes` writes a different table that no V2 read model reads (S4-07).
- The two verdict generations cannot be joined by a simple UI merge: `feedback_events.alert_id` and `analyst_verdict_events.operational_alert_id` are different stores, the vocabularies differ (five versus four, with `escalate` and `inconclusive` having no counterpart), and no live V2 read model reads `feedback_events` (S4-02).
