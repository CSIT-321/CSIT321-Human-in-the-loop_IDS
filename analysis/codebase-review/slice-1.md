## Challenges to the team's assumptions
- Fact 1 is a projection policy, not a hidden schema defect: nothing auto-projects legacy rows (no trigger/view; `materialize_source` is called only by `scripts/materialize_flow_queue.py`, fixtures and `admit_external`). The 996 stay `unassigned/staged` because `materialize_source` always writes the dormant triage defaults (`operational_v2.py:109-119`).
- Fact 2 is structural in the data dictionary: `analyst_verdict_events.operational_alert_id` and `analyst_work.operational_alert_id` reference only `operational_alerts_v2`, and `analyst_verdict._eligible` additionally requires an `operational_system_routing` row; no FK or view lets a legacy alert id reach those tables.
- Fact 3 is a writer bug, not a schema limit: `operational_triage_state_v2` permits `tier2_recommended=1` only with reasons (`operational_v2.sql:54-56,62`) and `evaluate_triage` computes them; `system_routing.py:101` discards them by passing `False` and `()`. The schema will accept the fix unchanged (but see S1-04 for the band storage).
- Fact 4 is reinforced by the schema: `trusted_context_facts` is an opaque append-only JSON log with no typed columns, no `created_at`/`context_key` (`trusted_context.sql:1-8`), and every consumer replays the whole log in Python (`context_store.py:45`, `trusted_context.py:123-139`). There is no schema path for a sensor/asset producer, so four routing rules can only ever see human or synthetic facts without a new producer design.
- Fact 5's wrong confidence is explained by two confidence fields, not lost data: the approved `alerts.confidence` is preserved as `source_provenance.legacy_fusion_confidence` (`operational_v2.py:24`, set in `adapters/operational_v2.py:40-42`), while the console reads `detector_confidence`, which `adapters/current.py:25-31` leaves NULL for corroborated legacy alerts. The other missing items also still exist in `alerts`, `flow_data`, `feedback_events`, `alert_families` and `alert_notes`; the V2 read model simply has no contract for them.
- The "one name per concept" goal is contradicted by the schema itself: four analyst-judgment vocabularies (S1-07), three band vocabularies (`alerts.queue_class`, stored `priority_band` labels, `priority_band_scheme`), two actor column names (`feedback_events.user_id` versus `actor_id` everywhere in V2), two confidence meanings, and eight separate append-only/audit logs (`audit_log`, `operational_routing_audit`, `operational_triage_policy_audit`, `tier2_case_events`, `analyst_verdict_events`, `analyst_work_events`, `triage_memory_audit`, `verdict_memory_evidence` variants).
