## Challenges to the team's assumptions
- **Fact 5 is partly a rendering gap, not a data gap.** Four items (AL short name, rule condition table, combined explanation, agreement) are already in the V2 evidence payload (S7-03). Claiming all 13 need data restoration overstates the migration work; conversely, treating the console as "already restored" understates the nine genuinely absent items (S7-04).
- **The "one wrong value" is recoverable without a backend change.** `sourceProvenance.legacyFusionConfidence` carries the approved 100.0% for AL-01958; the UI simply reads the canonical `confidence` field (S7-05). This is a display bug, not a projection bug.
- **Restoring the deleted components is simpler only for display.** The deleted cards (FlowPanelCard, FamilyPanelCard, FeedbackHistoryCard) plus the feedback components/tests exist at `f1b74b6`, the legacy endpoints are still mounted (`hitl-ids/apps/api/routes.py:174,255,293,353,361,420`) and the generated client still contains `FlowPanel`, `FamilyPanel`, `FeedbackResponse` and `ScoreAdjustment` types. For a `legacy_flow_alert` row the operational ref is the legacy `alert_ref`, so one extra GET restores the whole legacy detail. But restoring `FeedbackPanel`/`ScoreAdjustmentChain` would write `alerts.combined_score`/`queue_class`, which the V2 queue never reads (S7-04). The cheap path is: restore the display cards behind a source-kind gate, and rebuild the write path only after choosing one queue as the source of truth.
- **The team's own tests currently enforce the loss.** `hitl-ids/apps/web/src/pages/analyst/OperationalWorkstationPage.test.tsx:136` asserts no request path starts with `/api/alerts`, and the fixtures only model system-routed Suricata alerts. Any restore will necessarily change that test (S7-10).
- **The cleanup report's evidence-card claim is false at the tip.** The report in `c00c556` says the detector evidence cards remain because current Admin/Evaluator or audit views use them; `DetectorEvidence` has no production caller, and the three cards are reachable only through it (S7-07). The files are effectively orphaned, which actually makes them cheap to reuse.
- **The cleanup report's "legacy endpoints are internal compatibility" decision is reversed by the product goal.** The report explicitly kept the endpoints and removed the UI as a deliberate boundary; restoring the 13 items means reopening that boundary for `legacy_flow_alert` rows while keeping Suricata rows on V2.
- **The Tier 1 view the goal asks for is not the "Tier 1" queue tab.** The tab filters `handlingRoute='tier1_review'` (`hitl-ids/apps/web/src/features/alert/OperationalQueue.tsx:16`); the 996 unassigned flow alerts appear only in Active/All, labelled "Unassigned", and selecting one does nothing. The goal's "all incoming alerts plus Tier 2 candidates" is therefore a new view, not a relabel.
- **One name per concept is currently violated.** The codebase has `Operational Priority` (V2 triage score), `detection score` (immutable `alerts.detection_score`), `operational score` (legacy mutable `alerts.combined_score`), `queue band` (`alerts.queue_class`) and `priority band` (V2 P1-P4). The workstation prints "Operational Priority" while the approved page's "operational score" is absent; a rewritten data dictionary/UI spec must define all five separately.
- **Tier 2 "who escalated and why" is actually present.** The case detail shows creation source, handoff, escalation reason and routing actor (`hitl-ids/apps/web/src/pages/analyst/Tier2CasesPage.tsx:149,167-171`); the requirement is met on the detail page, so the remaining Tier 2 work is the candidate list/recommendation path (S7-02), not the detail provenance.
