## Challenges to the team's assumptions
- **Fact 6 is right about the failures but wrong about their single cause.** Two of the four tests fail because the live-tree `git diff` raises before the assertion under test (`test_protocol_v3.py:72-74` expects `opening receipt`, `:100-102` expects `hash mismatch`); one fails at `verify_amendment`'s `git rev-parse HEAD:<path>` (`amendment.py:34`), not at the tests' own tree comparison; one fails at `validate()`. `test_hash_tampering_is_detected` still passes, which proves the frozen bytes are intact and the problem is the predicate, not corruption.
- **The frozen V3.1 experiment cannot be opened from the development branch at all.** `open_protocol_v3_1.py:12` calls `validate()`, which is the same live-tree check. The protocol document says the runner uses a separate clean `RUNTIME_SHA` checkout (`docs/final-evaluation-protocol-v3.md:33,232-237`), but the preflight validates the tooling branch's product tree instead.
- **The four failing tests and the validators are themselves inside the artifact.** `evaluation/protocol-v3/manifest.json:127-128` and `evaluation/protocol-v3.1/manifest.json:158-161` hash `validate_protocol_v3.py`, `validate_protocol_v3_1.py`, `test_protocol_v3.py` and `test_protocol_v3_1.py`. Any in-place repair changes the evidence; the fix must be additive (new checker plus a skip in an unhashed `conftest.py`), not an edit or a re-freeze.
- **A fixed live-tree check still fails on the current product.** `apps/api/presentation_replay.py:23` imports `scripts.protocol_v3.common`, and the preflight's own boundary scan rejects that substring (`validate_protocol_v3.py:81-84`). This is a live product-to-evaluation coupling, not a historical artifact; it also makes the API require `evaluation/` at startup.
- **"V2 evaluation" does not cover the V2 product's routing generation.** The recorded prospective path requires `admit_tier1` (S9-03), and the temporal exporter rejects the duplicate policy/routing audits written by `system_route` (S9-04). Only the legacy single-event adapter path (`suricata-eve-v1`) and the current-memory counterfactual work; the product's automatic Suricata Tier 1 path is outside both recorded evaluations.
- **The Phase A count is deliberately 996, not 5,000.** `materialize_flow_queue.py:23` selects `evidence_class != 'none'`, and `tests/test_flow_queue.py` asserts that unflagged alerts are *not* projected. That is consistent with "incoming alerts", but the approved demo's bottom-band story is an unflagged alert: `rehearse_demo.py:49,153-155` uses `AL-03086` with `evidenceClass == "none"` and `queueClass == "none"`. The V2 workstation cannot reproduce that step unless the queue population is widened or the V2 narrative is rewritten.
- **The "one operator command" is not idempotent by design.** `run_detection.py` appends a detection run to an existing database; the docs warn to delete `data/demo.db` first. That is an operator footgun, not a code bug, but it belongs in the final runbook next to `materialize_flow_queue.py`, which *is* idempotent.
