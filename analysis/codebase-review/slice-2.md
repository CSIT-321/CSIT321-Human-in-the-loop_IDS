## Challenges to the team's assumptions
- **Fact 2 is worse than "cannot be claimed".** The visible manual escape is a dead end: `routing.allowed_actions` accepts `admit_tier1` from `unassigned/staged` (routing.py:67-73), so a client can be told the alert was admitted, but `is_tier1_work` (analyst_work.py:83-86) and `_eligible` (analyst_verdict.py:64-67) still require an `operational_system_routing` row that the manual route never writes. The current console even hides the action unless a system routing row already exists (`V2RoutingPage.tsx` builds actions from `view.systemRouting`). Do not treat a successful admit-tier1 as a working Tier 1 flow.
- **Fact 1's projection is a one-way copy, not a view.** `operational_alerts_v2` is immutable evidence (`materialize_source` refuses a changed projection) and `_projection` excludes the legacy operational fields (adapters/operational_v2.py:19-25). A legacy verdict, even a correct one through `/api/alerts`, cannot update what the V2 view shows. The fix has to choose a source of truth: either V2 reads the legacy row, or the legacy operational fields are projected and maintained in V2.
- **Fact 3: hard-coded `tier2_recommended=False` is only half the problem.** The approved E1/E3 result already exists in `alerts.queue_class` (644 `tier2_candidate` rows on the demo, per store.py:550-552), is never projected, and the V2 queue's ordering key for these rows (`operational_priority`) is NULL (operational_queue.py:18,64,77). Changing line 101 to a computed value still shows no E1/E3 reason unless the legacy state is projected.
- **Fact 7: `tier2_candidate` is E1 OR E3, and the shipped band is that OR.** `formulas.tier2_candidate` (formulas.py:151-154) returns true for E3 (`score >= 90 and class severity >= 7`), and `runner._place` stores the OR in `queue_class`. On the demo E1 is 200 and the band is 644; wiring `queue_class == 'tier2_candidate'` to automatic escalation would auto-escalate E3's false positives (342 on the stress DB). Automatic escalation must use E1 only; E3 may be a display reason for Tier 1 review.
- **The settled "queue order severity-first via `db.queue_order`" is not what the final product serves.** `db.QUEUE_ORDER_BY` and `store.queue_page` still implement it, but the final Tier 1 list is `operational_queue.queue_page`, ordered by `operational_priority DESC, occurred_at DESC` (operational_queue.py:64,77); every projected flow alert has NULL priority, so it falls to capture-time order. The approved severity-first order is reachable only through the legacy `/api/alerts` endpoints the console no longer calls.
- **Fact 5's confidence is not missing from the data.** `alerts.confidence` holds the fused value and `source_provenance.legacy_fusion_confidence` copies it. "Not provided" comes from `store.detector_for_alert` building the projection with `legacy_projection=True` and no prediction, and the adapter restoring confidence only for `ml_only`/`none` (store.py:40-41, adapters/current.py:29-32). Fix the projection/render, not the engine.
- **If "all incoming alerts" means the approved engine's definition (every flow, including the `none` band), the final view still omits 4,004 of 5,000 flows.** `runner.py:6-8` says every flow becomes an alert and the `none` band is the queue's bottom band; `scripts/materialize_flow_queue.py:8` decides unflagged flows are "not queue work". One definition has to win before the Tier 1 view can be described.
- **The V2 edits to `runner.py` and `store.py` did not break the feedback code — they bypassed it elsewhere.** The two changes are the detector snapshot in `runner.run_detection` (runner.py:110-114) and the read-time `detector_for_alert` fallback (store.py:25-41); neither touches `submit_feedback`, `apply_guardrails` or `refresh_family`, which still work when called directly. The engine becomes unreachable because the final Tier 1 view was replaced by the V2 queue/verdict path (S2-01/S2-02), not because these functions regressed. The one regression inside the modified pair is the legacy-projection confidence loss (S2-06).
- **One word, two generations.** `triage.py` (legacy status/owner/notes) and the V2 `analyst_work`/`routing`/`triage_policy` stack; `feedback_events` and `analyst_verdict_events`; `alert_families` and `triage_memory`; `audit_log` (the only trail `AuditWriter` writes) and the current-audit projection. The design documents cannot name "the verdict", "the queue" or "the audit trail" until one generation is chosen; today `/admin/audit` and `/admin/evaluation/audit` are two different histories of the same product.
