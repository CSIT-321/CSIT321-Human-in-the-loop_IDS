## Challenges to the team's assumptions

- **Fact 2 ("flow alerts are never routed, cannot be claimed and cannot receive a verdict") is incomplete.** The API does expose a human admission bridge (`admit-tier1`, allowed for `unassigned/staged` by `routing.py:67-69`), so "never routed" is a policy outcome, not an API impossibility. The real block is deeper: `is_tier1_work` and verdict `_eligible` additionally require an `operational_system_routing` row (`analyst_work.py:83-86`, `analyst_verdict.py:65-67`), which the legacy projection never creates, and `admit-tier1` does not run triage (`routing.py:133-137`). Any fix must address the eligibility coupling and triage evaluation, not just call an existing endpoint.
- **Fact 1's "0 alerts" turns into "996 unactionable rows", not a working queue.** `materialize_source` inserts a triage state with `operational_priority=None` and `priority_band=None` (`adapters/operational_v2.py:150-157`); the queue's `VALID_PRIORITY` deliberately sorts NULL last (`operational_queue.py:18`), and the API advertises `allowedActions: ["admit_tier1"]` on those rows (`routing.py:67-69`). The final workstation renders neither that action nor a claim path for them, so the materialiser alone does not satisfy Phase A/B.
- **The Tier 1 "candidates with reason" goal is not yet derivable as a set.** `RoutingView.state` carries `tier2_recommendation_reasons` (`contract/routing.py:43` -> `packages/contracts/operational_v2.py:117`), but `/api/v2/alerts` has no candidate filter (S6-05) and the final Tier 1 queue does not render those reasons (traced: `OperationalWorkstationPage.tsx` and `OperationalQueue.tsx` only use `systemRouting`/`effectiveReview`). After fact 3 is fixed, both the SQL filter and the row reason display are needed; without them the analyst can only see candidates by paging through everything.
- **The Tier 2 list cannot be scoped to "Tier 2 work".** `GET /api/v2/tier2/cases` has only `limit`/`offset` and orders by `id DESC` (`tier2_case_routes.py:35-42`; contract openapi.py:677-680), so resolved cases share the same pages as open ones. A status/owner filter (and a stable sort) is Phase D work; the summary's `open_tier2_cases` count cannot be used to page the list.
- **The published contract is no longer the "deliberately narrow" demo contract.** `openapi.py:152-153` still claims only the demo path is exposed, but the document now carries the whole V2 generation plus research/evaluation endpoints (external admission, selective review, triage memory, trusted context, prospective collection, workspaces/presentation replay, final V3.1). The final API document must be rewritten around the Tier 1/Tier 2 surface, not extended further (S6-08, S6-06).
- **Endpoint mapping for the final views (verified from `apps/web/src` callers).** *Tier 1 needs:* `listV2Routing`, `getV2AlertsSummary`, `getV2Routing`, `getV2AlertEvidence`, `getAnalystWork`, `claimAnalystWork`, `getAnalystVerdict`, `recordAnalystVerdict`, `getAnalystVerdictHistory`, `matchTriageMemory`, `getVerdictMemoryState`, `contributeVerdictMemory`, `getSelectiveReview`, `applySelectiveReview`, `requireHumanReview`, plus the SSE stream. *Tier 2 needs:* `listTier2Cases`, `getTier2Case`, `listTier2CaseEvents`, `addTier2CaseNote`, `recordTier2CaseFinding`, `recordTier2InvestigationConclusion`, `startTier2Investigation`, `resolveTier2Case`, `linkTier2CaseAlert`, `getTier2InvestigationAssistance`, the four response-plan operations, `contributeConclusionMemory`, `getConclusionMemoryState`. *Research-only for this goal:* external admission, prospective collection/export/report, final V3.1 evaluation, workspaces/presentation replay, current audit, trusted context, standalone candidate routing (`approve`/`reject`/`escalate`), the triage-memory list/activate/reject page, and the selective-review list/metrics/events page. The API slice is therefore wider than the final product needs; the contract should say so.
