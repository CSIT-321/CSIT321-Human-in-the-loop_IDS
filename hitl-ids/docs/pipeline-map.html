02The spine: flow in, alert out, verdict back

Detection is an offline batch, never inline in the API (decision D3). Every flow in the source becomes an alert — including the flows no detector flagged, which are the queue's bottom band and the evaluation's denominator. After detection the flow runs right-to-left: a human verdict writes to a family, and the family's learning is what a future alert reads.

The return arrow is the whole thesis. Feedback does not change the alert the analyst judged and stop. It writes to alert_families, and runner._place consults that table before banding a newly detected alert — so a verdict on Monday reorders the alerts a Tuesday batch produces. That is the confirmed project goal, and it is the only edge on this diagram that makes the system more than a review tool.

03How a signature and the model combine

This is the node the project re-specified. The original design fused the two detectors with a weighted sum; that was rejected, because scores from different evidence classes are not commensurable. What replaced it is a branch: the two detectors are combined by a rule about agreement, not by arithmetic across their scores.

Inputs, per flow

sig = max( severity_scores[match.severity] )   over every matching rule; 0 when none matched
      severity_scores: Low 0.40 · Medium 0.60 · High 0.80 · Critical 0.95

ml  = 1 - P(Benign)                            the model's malicious probability; 0 when unavailable
Two corrections that live in this step. The model's contribution is 1 − P(Benign), not the predicted class's confidence — the notebook's version understated it whenever probability was split across attack classes. And corroborated requires the model to agree on the class, not merely to also flag the flow: 23 NMAP probes of TCP/21 matched the FTP brute-force rule, which is a disagreeing claim, not corroboration.

What the branches actually produce

Measured on the 1,000-malicious-flow sample the project reports from:

ml_only794 corroborated200 signature_only0 missed by both6

Read that third number carefully — it is the finding that reshaped the project. The retuned signature rules reach precision 1.000 at recall 20%, but they add zero unique coverage. The signature layer's value is not that it catches what the model misses; it is that it gives a human a checkable reason (decision Q21: trust and explainability, not coverage). Any design that assumes the two detectors are complementary is building on a claim this data withdrew.

Read the "applied" column carefully — it is the non-obvious result. At the committed settings the caps never bind. Every category's requested change (+10, +15, 0, −15, −30) already lies inside the permitted range of [−30, +20], and a family's accumulated adjustment is clamped to those same bounds before it is ever proposed. So on the direct path the cap is defence in depth, not a working constraint — it exists for when an administrator reconfigures the bounds (NFR-08) and for a family whose arithmetic would otherwise run past them. The checks that actually fire are the floors and the 0–100 range clamp, which is exactly what the three-arm run measured: all 40 verdicts recorded as capped, every one of them the 100 ceiling rather than a guardrail cap.

06What orders the queue

One definition, in db.queue_order(alias), from which the queue, the API, the metrics module, the scenario module and cef.queue_key all derive. It had been written out in five places before this.

ORDER BY  severity   worst-first   Critical → High → Medium → Low → Informational
       ,  combined_score  DESC          the operational score feedback moves
       ,  id              ASC           stable tie-break
This changed, and the change is a correction. The order used to lead with queue_priority — the band. Because the band put Tier 2 candidates first, and a Tier 2 candidate need not be severe, the entire top 50 was Medium. Triage is urgency, so severity now leads.

Before — band-first

  • The band was the first sort key
  • Top 50: all Medium
  • A benign alert sat at rank 1
  • precision@50 fell to 0.980

After — severity-first

  • Severity leads, score breaks ties
  • Precision@50 held at 1.000
  • Zero false positives in the top 50, every arm
  • That benign alert moved to rank 186

What the band still does

  • Labels a Tier 2 escalation candidate
  • Orders the band tabs in the console
  • No longer decides queue position
  • Invariant I5 retired with it
Honest caveat, and the measurement behind it. Six candidate orders were compared on both databases. data/demo.db cannot judge an order — it scores precision 1.000 at every cut-off because its 996 flagged alerts hold only 2 false positives, so the test is saturated. data/stress.db can, and it prefers evidence-first (precision@100 1.000 vs 0.770). Severity-first stays the default anyway: it costs nothing on the real detector, and the contract gained an evidence sort so the suspect-model case is one click away. Remaining deltas are small and negative (precision@200 −0.010, mean rank −0.515) and are reported as measured.

07One verdict's journey

A verdict reaches a score only through the guardrail gates, and reaches other alerts only through the family. Both paths are below. The base is always the alert's detection_score: feedback does not stack, so an alert's score is its detection score plus the guarded change of its one effective verdict.

Then the family learns

The verdict is replayed over the family's effective verdicts — each member's latest, oldest first, so an amended verdict counts once. Alerts already carrying their own verdict are skipped, and a signature_override alert neither teaches its family nor learns from it.

The gate is strict at exactly the boundary you would test. Agreement is rounded to 4 places, as the collaborator's engine rounds it — so 2 of 3 is 0.6667, which fails a 0.67 gate. A family needs a clean 3-of-3, or 4-of-5, to move anything.

Worked through, with real chart values

A Web Attack family (CVSS 8.0, so w = 0.8) with three confirm_true_positive verdicts:

each confirmation   Δ = +30 × 0.8              = +24.0
after three         adjustment = 24 × 3        = +72.0
clamped to the cap  adjustment                 = +20.0   [−30, +20]

gate               3 verdicts, no tie, share 1.000 ≥ 0.67  → OPEN
movement M1        3 confirmations             → offset −3 bands

every member with no verdict of its own is re-scored:
    score = detection_score + 20.0   inside the guardrails, so a Critical member holds at 70

Note that the cap binds after three verdicts — more confirmations past that point change the band, not the score. That is the guardrail doing its job: without the positive cap, repeated "confirm true positive" would inflate a family's score without bound.

08How the formula was chosen — and how thin the win is

Section 06 said what the learning formula does. This section is about why that one — because it was not picked by preference. Sixteen candidate designs were simulated against a fixed set of metrics, and a rule written down before the run chose the winner. This is the part of the project an examiner will press on, so it is worth understanding properly.

The question being asked

When an analyst confirms or dismisses an alert, how much should that move the alert's family? Too little and feedback does nothing; too much and one mistake floods the queue. The project wrote four candidate answers, then tested them.

FormulaThe idea in plain wordsThe arithmetic
C0 · fixed step Every verdict moves the score the same amount, regardless of what kind of attack it is. The simplest possible rule. +10 / +15 / −30 / −15
by category, always
C1 · severity-weighted A confirmation of a serious attack should count for more than one on a port scan. So the step is scaled by how bad the attack type is. up: +k·w
down: −k·(1−w)
w = severity ÷ 10
C2 · Elo-style Borrowed from chess ratings. An unexpected verdict moves more than an expected one — confirming an alert that already scored 95 is no surprise, so it should move little. d = kdir·(1 − score/100)
kdir = k·(0.5 + 0.5w)
C3 · Elo + uncertainty Same as C2, but a family with only one verdict behind it is treated as untrustworthy and moves less than a family with twenty. C2 × max(0.4, 1/√(1+n/3))
n = prior verdicts

Each formula was also tested under two movements — how far the family moves between queue bands — and two family keys — how loosely "similar alerts" is defined:

M1 — one band at a time

A confirmation promotes the family one band. A dismissal demotes one band, but only after two dismissals (a safety margin, like a cooling-off period). Cautious.

M2 — straight to the top

A single confirmation jumps the family all the way to the top band. Fast — and riskier, because one verdict has immediate maximum effect.

coarse family key

Groups by attack class + port + protocol + rule. Broad: many alerts per family, so learning spreads widely.

fine family key

The same, plus more qualifying fields. Narrower: fewer alerts per family, so learning spreads less but is more specific.

4 formulas × 2 movements × 2 family keys = 16 candidate designs. All 16 were simulated; the table further down shows the result.

How the test was run

The simulation splits the alerts in half. A Tier 1 analyst works the first half only — confirming and dismissing — and the machine learns from those verdicts. The second half is then scored using what was learned. That second half is the whole point: it is made of alerts the analyst never saw, so any improvement there is real learning, not memorisation.

Two complications were built in deliberately, because a perfect analyst is not the realistic case:

  • Analyst error — the simulated analyst is given wrong beliefs at 5% and 15% error rates; the results below are quoted at 5%. A design that only works for an infallible human is not a design.
  • Three seeds — the whole experiment is repeated three times with different random choices, and the numbers are averaged. One lucky run proves nothing.

The metrics — what each measures, and what it would miss

These are the words the results table uses. Each was chosen for a reason; each has a blind spot. Knowing the blind spots is what makes the conclusion honest.

MetricPlain-English definitionWhy it was chosenWhat it misses
precision@k Look at the top k alerts in the queue. What fraction are genuinely attacks? Quoted here at k = 50, 100, 200. The queue is worked top-down, so the top of the list is what actually costs the analyst time. A detector can be 99% accurate overall and still be useless if the top 50 are junk. It says nothing below rank 200, and it is brutally insensitive when the detector is already near-perfect — a score of 1.000 cannot improve.
mean attack position Take every real attack. Where does it sit in the queue, as a fraction of the whole list? Average those. Lower is better. 0.0828 means the average attack sits about 8.3% of the way down. precision@k only counts the very top. This measures the whole queue, so it can still detect an improvement when precision is pinned at 1.000 — which is exactly the situation here. The differences involved are tiny, so it is easy to over-read them. It also averages: moving one attack from rank 900 to 800 looks the same as moving one from 10 to 9.
attacks demoted under error How many genuine attacks did wrong analyst feedback push down the queue? Measured at 5% and 15% analyst error, and summed. This is the safety question. Learning that improves the average while burying real attacks is a failure, not a success. It only counts attacks; it does not care how far they were pushed.
Tier 2 precision Of the alerts flagged as "escalate to Tier 2", what fraction are real attacks? Tier 2 is a scarce human resource. Sending false alarms there wastes the expensive analyst — the worst place to be wrong. It ignores volume entirely — see the next row.
Tier 2 load How many alerts land in Tier 2 at all. The control (no feedback) produces 243. Precision alone can be gamed by escalating almost nothing. Load is the counterweight: read alongside precision it says "how much work, how well aimed". Meaningless on its own. Low load with low precision is as bad as high load with low precision.
class_changes How many times an alert's queue band changed while learning was applied. A stability measure. A queue where alerts keep jumping between bands is confusing to work from — the analyst loses their place. This is not a triage-quality metric. It measures churn, not correctness. A design that moved nothing at all would score perfectly here — which is precisely why it sits below every outcome metric in the decision rule.
floor violations How many times feedback pushed a Critical (or Infiltration) alert below its protected minimum score. Should be zero. A hard safety property. Any non-zero value disqualifies a candidate outright. Nothing — it is a pass/fail gate, not a ranking metric.
false positives in top 50 How many benign alerts reached the top 50. Should be zero. The most visible failure mode: a false alarm at rank 1 destroys trust in the whole console. Again a gate rather than a gradient — but see section 12, where one design failed it.

The decision rule — a ladder, not a score

The selection rule is called sel-3 and was fixed before the run. Crucially it is lexicographic: it compares candidates on the first criterion, and only if they are exactly tied does it look at the second, and so on. It is not a weighted sum. That matters, because it means a difference of 0.0001 can decide the winner when nothing else separates two candidates.

sel-3 — applied in this order, stopping at the first difference

  1  Q27 conformity   does the step scale with attack severity?   C0 fails: fixed steps
  2  safety           no floor violation, no attack demoted at 0% error
  3  robustness       fewest true attacks demoted under analyst error
  4  escalation       highest Tier 2 precision
  5  triage           lowest mean attack position
  6  stability        fewest class changes
  7  parsimony        simplest formula, then movement, then family key
Read criterion 1 carefully. It is not a performance measure at all — it is a policy requirement (decision Q27: the adjustment must scale with how bad the attack type is). This single line is what eliminates C0, even though C0 performs as well as any candidate.

What this actually proves — and what it does not

Do not present C1 as the measured best. The honest reading of the table is that the experiment could not distinguish these designs. Look at the control row: with no feedback whatsoever, mean attack position is 0.0829 and Tier 2 precision is 1.0000. Every candidate sits within 0.0001 of that. There is almost nothing for feedback to improve, because the detector is already near-perfect on this sample — only 2 false positives in 996 flagged alerts. A test whose baseline is already perfect cannot rank improvements to it.

What is solid

  • The rule was fixed before the run, so the choice is not post-hoc
  • C1 is selected, and it is the simplest severity-scaled formula
  • Nothing was demoted, no floor was breached, no false positive reached the top 50
  • Every candidate is safe — the guardrails held in all sixteen

What is weak

  • The margin is 0.0001 — one ten-thousandth
  • C2 does not lose on merit; it loses on a rounding-level difference
  • C0 would win on raw numbers and is excluded only by policy
  • The sample is saturated, so the test has almost no discriminating power

What would settle it

  • A detector with a realistic error rate — the stress database
  • Then the metrics would have room to separate candidates
  • Designed already (ranking-and-escalation-design.md §8)
  • Not run — needs the project lead's go-ahead, and must be reported as a separate experiment

The movement choice is a deliberate override

One more thing a reader of the table will notice: sel-3's rank 1 is C1+M2, but the system runs C1+M1 (row 3). That is not an error — it is a recorded decision by the project lead, and it should always be described as an override rather than hidden.

The reason is a safety asymmetry. M2's only advantage here is class_changes (13.00 against M1's 25.33) — a measure of queue churn, not of triage quality, and it sits at criterion 6, below every outcome metric. Against that, an earlier run predating the agreement gate measured M2 at Tier 2 precision 0.7418 against M1's 1.0000, with double the Tier 2 load (504 against 243). M2 is only safe because the agreement gate restrains it; M1 does not depend on the gate to be safe. When a design's safety rests on a second mechanism, and its only measured benefit is queue tidiness, the cautious option is the defensible one.

The sentence to use in the viva. "The formula was chosen by a rule fixed before the run, not by preference. On this sample the severity-scaled candidates are statistically indistinguishable — 0.0001 apart on the only metric that separates them — because the control queue is already saturated. C0 would score best and is excluded by design decision Q27. The movement was overridden by the project lead on safety grounds, and the stress test is the experiment that would separate these designs."

09Escalation and the family key

Two definitions the loop depends on: what makes an alert a Tier 2 candidate, and what counts as "the alerts like it".

E1 — detector-driven

evidence_class == corroborated and is_critical. A checkable rule and the model agreeing on a severe verdict. All 200 demo corroborated alerts are real attacks.

E2 — analyst-driven

The verdict escalate, or confirm_true_positive on an attack type whose chart severity is ≥ 7.0. This is how a human escalates; it acts through promotion.

E3 — score-driven

Current score ≥ 90 and chart severity ≥ 7.0. High confidence on a severe type. A dismissal withdraws the candidacy.

Automatic escalation is post-demo (decision Q25). In the demo the console shows which alerts would go to Tier 2. Moving them is not built.

Grouping the queue by it

GET /api/alerts/families folds the queue into these groups, and the console has a Group by: None | Family control. It is grouping, not a second ranking: families are ordered by their best-ranked member's position in the contract queue order (section 06), and the endpoint does not accept sort at all — the parameter is absent from the document rather than ignored by the handler. familyKey is a queue filter, so a group reads its own members back through the ordinary endpoint, in the same order, from the same source.

On data/demo.db: 1,315 families over 5,000 alerts. Alerts with no family are excluded from the grouped view — a group of things similar to nothing is not a group — and remain in the ungrouped queue.

12The finding the project reports against itself

The three-arm evaluation did not produce the result the project wanted, and the honest version is the one to present.

Similar-alert learning works and does not leak — but on this sample it lowered precision. The control queue was already perfect (precision 1.000 out to k=200, with 2 false positives in 996 flagged alerts), so feedback could only break it. And it did: the coarse family key promoted a benign alert from rank 639 to rank 1, because its family was dominated by confirmed Web Attacks. Learning reached 198 untouched true positives and leaked onto 0 alerts outside judged families.

What this does not invalidate

  • The mechanism is sound and bounded
  • It leaked onto nothing outside judged families
  • Under the corrected v1.31 order, feedback no longer costs a top-50 place
  • Precision@50 holds at 1.000 in every arm

What it does expose

  • The coarse family key is the attack surface
  • A single family can carry a benign alert to the top
  • Arm C has no power as pre-registered — no dismissals occurred
  • The efficiency claim is still untested: a near-perfect control queue cannot show it

The experiment that would answer it

  • A stress test with a weaker or drifting detector
  • Designed in ranking-and-escalation-design.md §8
  • Not run — needs the project lead's go-ahead
  • Must be reported as a separate, clearly-labelled experiment
