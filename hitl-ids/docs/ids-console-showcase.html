Before the audience arrives

Build a clean database, then start two servers

Verdicts are permanent. The audit trail refuses UPDATE and DELETE, so a database that has been demonstrated on has already been judged. Rebuild it before every audience; it takes about 21 seconds.

The project has its own Python environment, hitl-ids\.venv: Python 3.11 with the exact library versions the tests, the demo database and the trained model were produced with (listed in requirements.txt). Activate it in every terminal you run Python commands in. After activating, a plain python means the project's Python, whatever other Python (for example 3.12) is installed on the computer. You also need Node.js 18 or newer for the console.

One verdict, end to end

  1. Browser. The analyst picks False Positive and clicks Record verdict. FeedbackPanel.tsx calls POST /api/alerts/{alertRef}/feedback through the typed client, which carries the signed-in account's Authorization: Bearer token.
  2. Vite forwards /api/… from :5173 to the API on :8000 (vite.config.ts).
  3. FastAPI (routes.py) validates the body as a FeedbackRequest, resolves the role and opens a database connection (deps.py).
  4. Feedback service (feedback/service.py) asks the guardrail policy how far the score may move, stores the verdict, updates the alert's score and band, runs family learning, and writes audit entries, all in one transaction.
  5. Mappers turn the stored rows into a FeedbackResponse: the requested change, what bound it, the applied change, and what the family learned.
  6. Browser draws the score-adjustment chain from that response. It never predicts the outcome locally, because only the guardrails know it.

Severity: how bad it is, not only how sure the model is

Five labels, and since 16 Sep 2026 all five occur. Severity is the band the operational score falls in — Informational below 1, Low from 1, Medium from 40, High from 70, Critical from 80 — and then capped by what the alert's attack class can reach. That second step matters. Confidence answers "how sure is the model?". It cannot answer "how bad is this?".

The ceiling is not a second opinion. It is the severity chart this project already keeps. config/severity-chart.json (decision Q27) gives every model class a CVSS v3.1 score, and that chart already decides Tier 2 candidacy and scales family movement. The ceilings are read from it: cef.ceilings_from_chart() maps each class's CVSS band onto the severity label. Edit the chart for one purpose and the severity ceiling moves with it. The two cannot disagree, because there is only one of them.

Until the ceiling existed, only two labels ever appeared — and that was a defect, not a property of the data. Severity was a function of the model's confidence alone, and the model is confident about everything it flags: the lowest malicious probability in the demo is 0.813, so every flagged alert cleared the Critical threshold. Measured on the old build, 994 of 996 flagged alerts read Critical, every one of the seven attack classes among them. A reconnaissance sweep and an intrusion were indistinguishable in the severity filter. The rebuild proposal had recorded the symptom — "severity in this data is only Critical or Informational" — without a cause.

Before we built — what the pre-analysis found

Notebooks 01–03, over frozen fixtures: the Infiltration mislabelling (above); the XGBoost retrain to 8 classes with native TreeSHAP explanations; and a held-out re-test of the tuned rules — precision 0.9999, recall 0.1993 over 250,655 unseen rows, 2 false positives in 30,025 hits. The assumption we withdrew. The plan assumed the two detectors were complementary. On corrected data they are not: the signature layer adds no detections, it adds a reason a human can check. Deep dive: what the notebooks actually tested

The notebooks in hitl-ids/notebooks/ are decision records, not results pages — every number is recomputed from artifact files, and superseded conclusions are shown rather than deleted. Three things they established:

How the data was split — and why the first split was wrong

The original split was a single 1,000-row sample, 50/50 benign/attack — 15× more attack-dense than reality, so any verdict-reordering experiment on it would be measuring a queue that never exists. Decision Q20 replaced it: a disjoint training sample of 250,655 rows and a 5,000-row demo sample (seed 20260911, stratified: 4,000 Benign + 7 attack classes) — disjoint, so the demo can never be a memorisation test. The tuned rules were then held-out re-tested over the 250,655 unseen rows: precision 0.9999, recall 0.1993, two false positives in 30,025 hits — the re-test that established the rules were not overfit to their tuning set.

Two splits, not one. The Q20 split is between the two samples. The model was then trained and tested on a second, internal split of the training sample: of its 250,655 rows, the model fitted on 200,524 and was tested on 50,131 it had never seen — an 80/20 stratified hold-out, seed 20260911, over 82 features. That held-out half is where every per-class figure comes from, and it is why they can be quoted at all: the demo sample played no part in training, and the held-out rows played no part in fitting. Eleven fields are refused to the model outright — Label, attack_class, is_attempted, Attempted Category, the source and destination addresses and ports, Flow ID and Timestamp — so the answer key cannot reach a detector even by accident. Precision 1.000 and recall 1.000 on six of the eight classes is therefore a genuine held-out result, not a memorised one; the two classes that are not perfect are the two the testbed barely contains — Infiltration (F1 0.913 on 55 held-out rows) and Web Attack (F1 0.993 on 76).

Why this model — what the tests said

The retrain was forced by the labels, not chosen for taste. The old 6-class model was trained on mislabelled data — it called SSH brute force “Benign” at 0.78 confidence, and it could not emit Infiltration at all, which is 8.3% of the demo data. The corrected labels plus Q19 (Port Scan split out: 99.6% of “Infiltration” was NMAP Portscan) forced the 8-class retrain; on corrected data the new model “catches those flows easily — a strong classifier subsumes weak rules”.

Near-perfect scores were treated as an accusation. In this testbed each attack class targets a fixed port (Botnet 100% on 8080, DoS/DDoS/Web Attack 100% on port 80), so a majority-class-per-port lookup alone scores ~83% accuracy — the model could just be reading the port. The port-shortcut hypothesis was tested by ablation and rejected: removing the port signal cost only −0.0011 macro F1. The model reads behaviour, not the port.

And the model family earns its place two ways: XGBoost on tabular flow features, and — decisively for a human-in-the-loop console — native TreeSHAP, which is what makes the toward-and-away evidence panels possible. The family was later confirmed by a recorded bake-off (notebook 07, identical features, folds and protocol: Logistic Regression collapses to 0.51 macro F1 at 78.7% accuracy — accuracy hides the rare classes; Random Forest 0.962; XGBoost 0.966 ± 0.015 and HistGradientBoosting 0.969 ± 0.011, a statistical tie) — the incumbent retained on the tiebreak that matters: explainability native to the family.

A second, weaker model — so the false positives are real

Why we built one. The strong model is the problem as much as the achievement. On this testbed it is so accurate that the demo queue holds 2 false positives in 996 flagged alerts, and precision is 1.000 at every cut-off to k = 200. Analyst feedback therefore has nothing to correct and can only disturb a perfect ordering — which is exactly what S15 measured under the old band-first order, when precision@50 fell 1.000 → 0.980. The v1.31 severity-first order removed that specific harm — precision@50 now holds at 1.000 in every arm — but the underlying problem stands: what feedback costs on this sample is a small shift in mean rank, not a gain in precision. The efficiency claim our thesis rests on cannot be tested against a queue that is already perfect, and ranking-and-escalation-design.md §8 has said so since v1.13.

What we did. We built a deliberately weaker detector and ran the real pipeline over it, into a separate database (data/stress.db) so the pristine demo is untouched. Nothing about it is invented. For every flow it degrades, the builder copies the complete prediction record of a real attack flow from the committed inference output. Every class, probability, confidence, margin and TreeSHAP attribution in it is an unfabricated output of the same committed model — only the association between a flow and a prediction is synthetic, which is precisely what "a detector that is struggling" means: the detector reports on this flow what it really said about a different one.

The degradation is seeded and reproducible (scripts/build_stress_detection.py, seed 20260916): 600 false positives, 15% of the 4,000 benign flows, each given a real attack's record and spread evenly across the seven classes; and 300 false negatives, 30% of the real attacks, each given a real benign flow's record, so the detector also misses what it used to catch. The builder prints its own manifest, and the file it writes carries a notice that it must never be presented as a measurement of the model.

A bonus: the weakened detector produced 52 signature-override alerts — the evidence class that has zero instances on the real data, so invariant I3 (a disputed rule's score is frozen) becomes testable for the first time.

The ranking experiment: three runs, pre-registered

Notebooks 05–06 chose the feedback formula the queue runs on. Four candidates (C0 fixed-step, C1 severity-weighted, C2 Elo-style, C3 Elo + uncertainty) × two movement rules (M1 one class at a time, M2 straight to top). Run 2 failed instructively: single verdicts were moving whole families — one correct dismissal of a benign flow the model scored 99.89 collided with real attacks. That failure produced decision Q30 (the agreement gate: ≥ 3 verdicts, dominant ≥ 0.67, no tie). Run 3 was pre-registered — selection rule sel-3 was committed to git before any run-3 number existed (the notebook dates the commit against the run's start), and it named C1 + M2. The project lead adopted C1 + M1 instead, because sel-3's movement pick rested on a metric the analyst never sees — each family's internal class state, including changes the gate withholds from the queue. Every metric the analyst does see is identical for M1 and M2 under the gate. C1 won on three counts: it is the candidate that satisfies the severity requirement, it leads the field on mean attack position (0.0828 against 0.0829 for the Elo forms, about a quarter of one queue position), and it is the simplest of the severity-scaled options. Say the honest version too: its edge rests as much on the requirement and on simplicity as on measured performance, because on this testbed the detector is too good for the formulas to separate.

Shipping it to a customer

What ships today is a lab appliance: an offline batch pipeline, a SQLite database, the API and the built console, three seeded accounts. It replays recorded traffic — by design, for evaluation.

The production path is planned, not improvised:

  1. Flow ingestion (S17). A CICFlowMeter-fork exporter turns the customer's SPAN/TAP/PCAP into the same feature schema the model trained on — the dataset's provenance is what guarantees no train/serve skew.
  2. Backend hardening (S18). PostgreSQL (the schema was written for it in S2), real user management and provisioning instead of seeded accounts, the remaining endpoint surface, append-only guarantees re-proven on Postgres.
  3. Deployment shape. On-prem, as a container/VM beside the customer's existing SIEM — the pipeline and its database stay on the customer's site. A SOC does not ship its flows to a vendor, and we do not ask it to.
  4. Per-customer configuration. Guardrail settings and the severity chart are admin-configurable at runtime and snapshotted per run; model and rule versions are recorded on every run, so any past decision is replayable.
  5. Rollout pattern. Replay the customer's historical flows first (shadow mode), tune the guardrails on their traffic, then put Tier 1 on the console beside the incumbent IDS — the ranked queue and the two score columns make the cutover observable, not a leap of faith.

Replacing the layer — or sitting beside whatever they already run

The layer we replace is not the sensor; it is the detection-and-triage layer — the ranked queue the analyst actually works. And the integration decision that matters most was made by refusing to write a parser per vendor: we read the wire, not the other IDS's output. Every IDS has a different output format, but they all watch the same packets; our exporter (S17, a CICFlowMeter fork) taps the same SPAN/TAP mirror and emits exactly the feature schema the model was trained on. The integration surface is the mirror port, not a vendor SDK.
